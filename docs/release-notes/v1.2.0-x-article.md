# llmff v1.2 is now available

llmff v1.2 is out.

This release adds declared multi-agent topology to manifests: reusable agent
role bundles and a per-stage `agent:` reference that names the roles in a
pipeline.

The goal is not to turn llmff into a multi-agent orchestrator.

The goal is to give multi-role workflows the same properties that make the rest
of llmff useful:

- explicit manifests
- bounded execution
- typed validation
- reproducible runs
- JSONL traces
- machine-readable inspect output
- clear subprocess semantics for supervisors

Multi-agent shapes are everywhere in current LLM systems.

A planner that hands work to an executor.

A critic that reviews a generator before output is accepted.

A debate between roles that a judge resolves.

A triage step that routes a request to the right specialist.

Most frameworks handle those patterns by making the runtime more dynamic, with
agents that decide at runtime who runs next. llmff v1.2 takes the opposite path:
the roles are declared, the topology is fixed, and the whole graph is still
visible before it runs.

## What landed

An agent is a reusable bundle of a persona plus model and sampling settings:

```yaml
agents:
  critic:
    model: mock:good
    response_format: json
    system: |
      You are the Critic. Return {"accept": boolean, "issues": [string]}.

graph:
  - id: review
    op: infer
    agent: critic
    from: draft
```

A stage references a role with `agent: <name>`.

The reference is expanded at inspect time into the stage's inference fields, so
the result is still a bounded, declared DAG. There is no new control-flow op.

Stage-level fields always override the referenced agent's defaults, so a role is
a default preset, not a lock.

This is the important distinction: llmff v1.2 supports multi-role pipelines, but
keeps them inside the same declared execution contract.

## Personas without a separate stage

An agent carries its persona in `system`. When a stage resolves a persona, the
runtime prepends it as a system message unless the assembled messages already
lead with one.

That means a role bundles its instructions, its model, and its sampling in one
place, and three roles in a pipeline read as three named agents instead of three
hand-wired system stages.

## Role-stamped traces

Every stage that references a role now carries the role name in its trace and
event records:

```json
{
  "event": "stage_finished",
  "stage_id": "review",
  "agent": "critic",
  "op": "infer",
  "status": "success"
}
```

That means a supervisor, dashboard, or trace summary can attribute work to a
named role, not just a stage id.

If a generator drafted, a critic rejected, and a reviser fixed the output, the
trace makes that obvious without log scraping.

## Inspectable roles

`llmff inspect --format json` now reports the resolved `agent` for each stage.

Because the reference expands at inspect time, the resolved model and sampling
are visible before execution, and a supervisor can see exactly which roles a
manifest declares and what each one will run.

## Bounded handoff

Handoff between roles is in scope when it stays declared and finite.

A triage role can label a request, and `route` selects the matching specialist's
output from a fixed set of named agent stages. The set of targets is in the
manifest and visible to inspect.

What stays above the boundary is dynamic dispatch: a role choosing an undeclared
or unbounded successor, spawning sub-agents, or driving open-ended agent-to-agent
handoff. That is task decomposition and coordination, and it remains a host
concern.

`agents:` names the roles. It never decides which role runs next at runtime.

## Runnable examples

The v1.2 examples are offline-first and covered by the example catalog test:

- generator / critic / reviser in a bounded refine loop
- planner / executor pipeline with typed schemas between roles
- debate / judge panel
- triage / specialist bounded handoff over `route`

Each example can be inspected without provider credentials and run with the mock
backend.

## Compatibility

v1.2 keeps the existing manifest, inspect, trace, and event contracts additive.

Older manifests parse unchanged, older inspect and trace records still validate,
and the new `agents`, `agent`, and `system` fields are validated when present.
The published JSON schemas were updated in the same release.

The release also keeps compatibility with the existing ecosystem work:

- Python subprocess supervisor
- batch supervisor
- Node.js streaming supervisor
- agent runner adoption guide
- OpenTelemetry bridge
- ecosystem readiness checks

The result is a way to declare multi-role pipelines without changing llmff's
boundary.

llmff remains an execution layer.

It is not a planner, memory system, serving layer, scheduler, or autonomous
agent runtime.

Those systems can sit above llmff.

llmff gives them a bounded, typed, inspectable process to run.
