# llmff v1.1 is now available

llmff v1.1 is out.

This release adds bounded loop and map execution for LLM pipelines, plus the
typed helper stages needed to make common refinement patterns runnable instead
of aspirational.

The goal is not to turn llmff into an agent framework.

The goal is to give agentic and refinement workflows the same properties that
make the rest of llmff useful:

- explicit manifests
- bounded execution
- typed validation
- reproducible runs
- JSONL traces
- machine-readable inspect output
- clear subprocess semantics for supervisors

Loops are everywhere in current LLM systems.

Retry a tool call.

Refine an answer until it validates.

Repair JSON until it matches a schema.

Sample several candidates and keep the best one.

Run a small critique step before accepting output.

Apply a bounded body graph to each item in a JSON list.

Most frameworks handle those patterns by making the runtime more dynamic. llmff
v1.1 takes the opposite path: loops and maps are declared pipeline stages, with
hard bounds and visible execution state.

## What landed

The loop stage looks like this:

```yaml
graph:
  - id: load_question
    op: load
    input: question

  - id: build_prompt
    op: template
    from: load_question
    path: prompt.tmpl

  - id: refine
    op: loop
    from: build_prompt
    max_iterations: 5
    break_on:
      type: field_true
      stage: ready
      field: passed
    body:
      - id: draft
        op: infer
        from: input
        model: mock:good
        response_format: json

      - id: check
        op: validate_json
        from: draft
        schema: '{"type":"object","required":["answer","confidence"]}'

      - id: ready
        op: predicate
        from: check
        field: confidence
        mode: gte
        value: 0.8
    final:
      from: draft
```

`max_iterations` is required.

There is no unbounded loop mode.

A loop can stop because its break condition fired, because it reached its
iteration bound, or because an error policy stopped the body. That stop reason
is part of the loop output metadata.

This is the important distinction: llmff v1.1 supports iterative execution, but
keeps it inside a bounded execution contract.

## Typed loop-body operations

The first loop implementation proved the execution model. The full v1.1 surface
adds the deterministic stages that make loop bodies useful without adding a
general scripting language:

- `extract` pulls a field or JSON path out of a typed value.
- `predicate` turns a value check into an explicit `{ "passed": true }` signal.
- `accumulate` carries bounded arrays or objects forward through declared
  `initial_carry` and `carry` wiring.
- `score` normalizes candidate scoring into JSON.
- `select` chooses from retained loop iterations, such as highest-score
  best-of-N output.

That combination supports the practical patterns people ask for: self-refine,
ReAct-style tool loops, iterative fact checking, and best-of-N selection.

The important part is that each operation is still inspectable. There is no
hidden Python expression, no implicit memory store, and no unbounded agent loop
inside the runtime.

## Break conditions

v1.1 supports the practical break conditions needed for the first release:

- `stage_success`
- `stage_failure`
- `field_true`
- `field_equals`
- `never`

That covers the common refinement, validation, retry, and fixed-count sampling
patterns without introducing a general-purpose programming language into the
manifest.

The loop body is still a normal subgraph. Existing stages such as `infer`,
`template`, `validate_json`, `route`, `tool`, `cache`, `retrieve`, and `write`
keep their usual semantics inside the body.

## Bounded map

v1.1 also adds `op: map` for bounded in-pipeline item processing:

```yaml
graph:
  - id: load_payload
    op: load
    input: payload

  - id: map_names
    op: map
    from: load_payload
    items_from: items
    max_items: 3
    body:
      - id: name
        op: extract
        from: item
        field: name
```

`max_items` is required. Default execution is sequential. If a manifest opts in
with `parallel: true`, it must also declare `max_concurrency`, and output order
is still deterministic by item index.

This is not a replacement for `llmff --batch-input`. Batch mode runs the whole
manifest once per input line and gives supervisors per-item artifacts. `op: map`
is a stage inside one run, useful when the collection is part of the payload.

## Per-iteration tracing

The tracing work is the part I am most excited about.

Every loop-body trace and event record can now carry loop context:

```json
{
  "loop_id": "refine",
  "loop_iteration": 2,
  "loop_stage_id": "draft"
}
```

That means a supervisor, dashboard, CLI trace summary, or debugging script can
see not only that a stage ran, but which loop and iteration produced it.

Map body records get the same treatment:

```json
{
  "map_id": "map_names",
  "map_index": 2,
  "map_stage_id": "name"
}
```

That gives dashboards and trace tooling enough structure to show bounded
collection progress without parsing synthetic stage names.

This matters because iterative LLM workflows can become opaque quickly.

If iteration 1 validated, iteration 2 failed, and iteration 3 repaired the
output, the trace should make that obvious without log scraping or framework
magic.

## Inspectable bounds

`llmff inspect --format json` now reports loop and map metadata:

- body stage count
- maximum expanded stage count
- break condition
- final output source
- item source and item cap for maps
- map parallelism and concurrency cap when present

This keeps loops and maps visible before execution.

A supervisor can inspect a manifest and understand the upper bound of work
before running it. That is especially useful for CI, batch jobs, queue workers,
and agent runners that need cost and runtime guardrails.

## Runnable examples

The v1.1 examples are offline-first and covered by the example catalog test:

- self-refining answer loop
- ReAct-style tool loop with a local command fixture
- best-of-N sampling with retained scoring and downstream selection
- iterative research and fact checking with retrieval and accumulated claims
- bounded map over JSON items

Each example can be inspected without provider credentials and run with the
mock backend.

## Compatibility

v1.1 keeps the existing inspect report contract additive.

That was a deliberate release gate: older inspect JSON reports still validate
against the current schema, while new loop metadata is validated when present.

The release also keeps compatibility with the existing ecosystem work:

- Python subprocess supervisor
- batch supervisor
- Node.js streaming supervisor
- agent runner adoption guide
- OpenTelemetry bridge
- ecosystem readiness checks

The result is new control-flow and collection primitives without changing
llmff's boundary.

llmff remains an execution layer.

It is not a planner, memory system, serving layer, scheduler, or autonomous
agent runtime.

Those systems can sit above llmff.

llmff gives them a bounded, typed, inspectable process to run.
