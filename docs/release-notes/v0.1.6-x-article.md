# llmff v0.1.6 is now available

llmff v0.1.6 is a functionality hardening release.

The previous release made the agent harness contract concrete with
`llmff run --run-dir`: a bounded subprocess model where agents and automation
systems can hand work to llmff, observe stable artifacts, and treat the process
exit code as the final authority.

v0.1.6 tightens that model.

This release focuses on the practical details that make llmff more useful in
real production-style workflows:

- supervised batch execution
- interrupted-run results
- consistent manifest fingerprints
- schema-backed run-result fixtures
- provider readiness documentation
- plugin promotion and trust fixtures
- real-world workflow examples
- stronger release preflight coverage

The direction remains the same: llmff is becoming a dependable FFmpeg-style
runner for LLM inference pipelines.

It should be boring in the best way: explicit inputs, reproducible manifests,
inspectable execution, restartable runs, local artifacts, stable JSON outputs,
and clear process semantics.

## What Is llmff?

llmff is a command-line and library tool for running typed LLM inference
pipelines.

It supports YAML manifests and compact inline graphs for workflows such as:

- JSON repair
- summarization
- structured extraction
- classification
- RAG-style retrieval and answering
- batch processing
- tool calling
- provider fallback
- cost and latency comparison

llmff is not a full agent framework.

It does not own planning, memory, autonomous loops, goal management, or
multi-agent coordination.

Instead, it is designed to be the execution substrate that agents,
applications, shell scripts, CI jobs, queue workers, and scheduled automation
can call as a bounded subprocess.

An agent or supervisor decides what should happen.

llmff performs the pipeline work.

The supervisor observes lifecycle events, traces, checkpoints, result files,
declared outputs, and the process exit code.

That boundary is the point.

## Highlights in v0.1.6

### Supervised Batch Execution

`llmff run --run-dir <dir>` now supports explicit batch input and batch output
paths.

That means a supervisor can run batch work while still getting the same
run-scoped contract:

```bash
llmff run pipeline.yaml \
  --run-dir .llmff/runs/job-42 \
  --batch-input inputs.jsonl \
  --batch-output-dir outputs
```

The run directory continues to own the supervision artifacts:

```text
inspect.json
trace.jsonl
events.jsonl
checkpoint.json
result.json
```

Batch runs also write per-item outputs and a batch report.

This matters for automation because batch work is rarely all-or-nothing in
practice. Supervisors need to know which item failed, why it failed, what exit
code applies, and whether a retry is reasonable.

v0.1.6 preserves structured failure information in batch reports, including:

- exit code
- failure kind
- safe failure message
- retry recommendation

Batch traces also include batch item completion records, and checkpoints record
completed batch item progress.

The result is a batch execution model that can be inspected and supervised
without scraping logs.

### Interrupted Runs Produce Structured Results

Production jobs get interrupted.

Terminals close. Workers receive shutdown signals. CI jobs are cancelled.
Supervisors stop jobs intentionally.

v0.1.6 makes interrupted `--run-dir` executions write a structured
`result.json` when possible.

Interrupted runs use:

```text
failure.kind = "interrupted"
exit_code = 130
retry_recommendation = "resume_with_matching_checkpoint"
```

That gives a supervisor a stable way to distinguish interruption from stage
failure, validation failure, timeout, or usage error.

The process exit code still matters. The result artifact mirrors that status
for systems that persist run directories after the process exits.

### Consistent Manifest Fingerprints

llmff already exposes manifest hashes through its inspect, result, and
checkpoint surfaces.

v0.1.6 normalizes those public hashes so supervisors can compare the same
manifest fingerprint across:

- `inspect.json`
- `result.json`
- `checkpoint.json`

This is small but important.

If a supervisor is deciding whether a checkpoint belongs to a run, or whether a
result corresponds to the inspected manifest, the comparison should be direct
and reliable.

### Schema-Backed Result Fixtures

v0.1.6 adds golden run-result fixtures for:

- successful runs
- stage failures
- interrupted runs

These fixtures are validated by the schema contract checks.

The goal is to make downstream integration safer. If an agent harness,
dashboard, CI adapter, or queue worker depends on llmff's result shape, it
should have a concrete contract to test against.

The schema surfaces now cover the parts of llmff that external tools are most
likely to consume:

- pipeline manifests
- traces
- lifecycle events
- run results
- plugin manifests
- plugin validation reports

### Compatibility Matrix

This release adds a core contract compatibility matrix covering recent llmff
releases.

The matrix tracks support across:

- manifest schema surfaces
- lifecycle events
- trace records
- run-result artifacts
- plugin protocol fixtures
- machine-readable CLI outputs

For a young project, this is a useful forcing function.

It makes compatibility promises visible, and it gives future releases a place
to record additive changes, deprecations, and contract expectations.

### Real-World Workflow Examples

v0.1.6 adds practical examples under:

```text
examples/real-world/
```

The examples cover:

- CI job integration
- queue worker integration
- scheduled job integration
- failure triage

These are intentionally ordinary.

They show how to invoke llmff as a subprocess, pass explicit inputs, capture
artifacts, read `result.json`, classify failures, and make bounded retry or
escalation decisions.

That is the intended integration model for agent systems too.

The agent can plan.

llmff can run the pipeline.

The supervisor can observe and decide what happens next.

### Provider Readiness

Provider documentation now has a clearer support model.

v0.1.6 adds or expands docs for:

- OpenAI-compatible servers
- Ollama
- Anthropic-compatible usage
- Azure OpenAI
- LM Studio
- vLLM
- LocalAI
- OpenRouter
- Together
- Groq

The release also adds provider support tiers and live smoke history.

Live provider smoke tests remain opt-in. They require explicit maintainer
secrets and runner expectations. Default validation remains offline and
deterministic.

That split is intentional.

The project should make provider confidence visible without making ordinary
local tests depend on external credentials or network availability.

### Plugin Ecosystem Groundwork

v0.1.6 continues building the plugin ecosystem surface.

This release adds:

- plugin promotion policy
- registry trust metadata
- reviewed protocol-v1 fixture records
- stronger plugin fixture validation

Example plugin review records now cover:

- retrieval providers
- rerankers
- model backends
- samplers
- tool transports
- postprocessor-style stages

This does not make the plugin ecosystem "done."

It does make the path more explicit: what can be promoted, what needs review,
what metadata is expected, and how fixture quality is checked.

### Stronger Release Preflight

The release preflight now validates more of the public integration surface.

Before tagging, the release gate checks:

- schema contracts
- manifest reproducibility
- plugin fixtures
- provider smoke readiness
- ecosystem readiness
- agent adoption guide
- OpenTelemetry bridge
- real-world workflow examples

That matters because llmff is not just a CLI with human-readable output.

It is exposing machine-readable contracts that other tools may build on.

Those contracts need local gates.

## Install

Install with Cargo:

```bash
cargo install --git https://github.com/syndicalt/llmff --tag v0.1.6 llmff
```

Or download release artifacts from GitHub:

```text
https://github.com/syndicalt/llmff/releases/tag/v0.1.6
```

The release includes:

- Linux archive
- Debian package
- Arch metadata
- macOS Apple Silicon archive and unsigned `.pkg`
- macOS Intel archive and unsigned `.pkg`

## Where This Fits

The goal for llmff is not to become an agent framework.

The goal is to become a dependable runner for LLM inference pipelines.

For agent systems, that means llmff can be used as a bounded execution tool:

- the agent decides what needs to happen
- llmff performs the pipeline work
- the supervisor observes files and process state
- downstream tools consume stable JSON artifacts
- failures are classified without scraping logs
- completed work can be checkpointed and resumed

This is the same broad reason FFmpeg became so useful for media workflows.

It gave scripts, applications, and larger systems a process-shaped tool with
predictable semantics.

llmff is trying to bring that style of execution boundary to LLM pipelines.

v0.1.6 is not a flashy release.

It is a hardening release.

It makes the supervised runner contract more useful for batch jobs,
interrupted jobs, provider onboarding, plugin review, and real-world
automation.

That is the kind of progress llmff needs if it is going to become boring
enough to build on.
