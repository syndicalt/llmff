# llmff v0.1.5 is now available

llmff v0.1.5 continues the direction of making llmff a dependable
FFmpeg-style runner for LLM inference pipelines, with a particular focus on
agent workflows.

The core idea behind llmff is that LLM pipeline execution should be explicit,
observable, reproducible, restartable, and easy to supervise from the outside.

Agents should be able to decide what needs to happen, hand bounded work to a
dedicated runner, and then monitor that work through stable process semantics
and machine-readable artifacts.

v0.1.5 turns that model into a more concrete contract.

## What Is llmff?

llmff is a command-line and library tool for running typed LLM inference
pipelines.

It supports YAML manifests and compact inline graphs for workflows such as:

- JSON repair
- summarization
- structured extraction
- classification
- RAG-style retrieval and answering
- batch processing
- tool calling
- provider fallback
- cost and latency comparison

llmff is not a full agent framework.

It does not own planning, memory, autonomous loops, goal management, or
multi-agent coordination.

Instead, it is designed to be the execution substrate that agents,
applications, shells, and automation systems can call as a bounded subprocess.

An agent can invoke llmff, pass explicit inputs, observe lifecycle events,
collect traces, resume from checkpoints, classify failures, and treat the
process exit code as the final source of truth.

## Highlights in v0.1.5

### Run Directories for Agent Supervision

The major addition in v0.1.5 is:

```bash
llmff run --run-dir <dir> pipeline.yaml
```

This creates a run-scoped artifact directory containing:

```text
inspect.json
trace.jsonl
events.jsonl
checkpoint.json
result.json
```

Each file has a distinct purpose.

`inspect.json` describes the run before execution: manifest hash, inputs,
outputs, stage order, backend configuration, execution options, stdout
ownership, and schema compatibility.

`events.jsonl` is the lifecycle event stream for supervision.

`trace.jsonl` is the execution trace for debugging, metrics, summaries, and
post-run inspection.

`checkpoint.json` is the resume state for completed stages.

`result.json` is the final machine-readable run result.

This gives agent systems a simple contract: create a run directory, start
llmff, monitor files, wait for exit, read `result.json`, and collect declared
outputs.

### Stable result.json

v0.1.5 introduces a schema-backed `result.json` contract.

A successful run writes:

```json
{
  "schema_version": 1,
  "status": "succeeded",
  "exit_code": 0,
  "manifest": {
    "hash": "sha256:..."
  },
  "artifacts": {
    "inspect": "inspect.json",
    "trace": "trace.jsonl",
    "events": "events.jsonl",
    "checkpoint": "checkpoint.json"
  },
  "failure": null
}
```

Failed runs write the same top-level shape with a structured failure object:

```json
{
  "status": "failed",
  "exit_code": 20,
  "failure": {
    "kind": "stage_execution",
    "message": "...",
    "retry_recommendation": "check_stage_or_input"
  }
}
```

This is important for supervisors.

An agent or orchestration system does not have to scrape stderr or infer state
from partial logs. It can read a stable JSON result and make a bounded
decision.

The process exit code remains authoritative. `result.json` mirrors that status
for downstream systems that persist artifacts after the process exits.

### Result Schema v1

The release adds:

```text
docs/schemas/run-result-v1.schema.json
```

This schema freezes the shape of `result.json` for downstream tooling.

The schema covers:

- schema version
- success/failure status
- exit code
- manifest hash
- artifact names
- failure kind
- safe failure message
- retry recommendation

This joins the existing schema v1 surfaces for manifests, traces, lifecycle
events, inspect reports, plugin manifests, and plugin validation reports.

### Agent Harness Contract

v0.1.5 adds a dedicated agent harness contract:

```text
docs/agent-harness-contract.md
```

The contract documents how an agent system should treat llmff as a bounded
subprocess runner.

It covers:

- process semantics
- run directory layout
- stdout ownership
- exit-code behavior
- artifact separation
- failure kinds
- retry posture
- safe metadata handling
- OpenAI Agents SDK adapter pattern
- LangGraph adapter pattern

The stdout ownership rules are especially important.

Only one thing should own stdout:

- lifecycle events
- a streamed stage payload
- a manifest output
- human-readable CLI output

For agent workflows, the recommended pattern is file-backed metadata through
`--run-dir`, not mixing events and payloads on stdout.

### OpenAI Agents SDK and LangGraph Examples

This release adds adapter examples under:

```text
examples/agent-harnesses/
```

The examples show how to wrap llmff as:

- an OpenAI Agents SDK tool
- a LangGraph-compatible node

The examples are intentionally subprocess-based.

They do not make llmff an agent framework. They let the host framework own
planning, memory, graph control, and user-facing reasoning, while llmff owns the
bounded pipeline execution.

The adapters materialize run-scoped manifests and inputs from a placeholder:

```text
{{LLMFF_INPUT_PATH}}
```

That matters because concurrent agent calls must not share or overwrite the
same input file.

Each run gets its own directory, its own materialized manifest, its own input
file, and its own result artifacts.

### Conformance Checks

v0.1.5 adds:

```bash
scripts/check-agent-harness-conformance.sh
```

This validates the run-directory contract with deterministic mock-backed runs.

It checks successful execution and failure behavior, including:

- required artifact creation
- valid `result.json`
- trace and event files
- manifest hash presence
- stage-execution failure classification
- exit-code behavior

This gives the agent-harness contract a runnable local gate instead of only
documentation.

## Install

Install with Cargo:

```bash
cargo install --git https://github.com/syndicalt/llmff --tag v0.1.5 llmff
```

Or download release artifacts from GitHub:

```text
https://github.com/syndicalt/llmff/releases/tag/v0.1.5
```

The release includes:

- Linux archive
- Debian package
- Arch metadata
- macOS Apple Silicon archive and unsigned `.pkg`
- macOS Intel archive and unsigned `.pkg`
- Windows `.zip`
- Windows unsigned MSI
- SHA-256 checksums
- release trust manifest

Authenticode signing, Apple Developer ID signing, and notarization remain
future paid distribution tracks.

## Where This Fits

The direction for llmff is to become a dependable FFmpeg-style runner for LLM
inference pipelines.

That means:

- boring process semantics
- explicit inputs
- reproducible manifests
- inspectable execution
- restartable runs
- stable machine-readable outputs
- local-first observability
- bounded subprocess integration

For agent systems, llmff is meant to be the execution tool, not the agent
brain.

The agent decides what should happen.

llmff performs the pipeline work.

The supervisor observes files, traces, lifecycle events, checkpoints, exit
codes, and result records.

v0.1.5 is a focused release, but it is an important one: it gives agent
workflows a concrete run directory contract and a stable result artifact to
build around.
